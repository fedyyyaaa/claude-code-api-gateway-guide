# 00. 我们自己的系统大概长什么样

> **仅供参考。**
>
> 这个仓库里的接法来自我们自己的项目。你的前端、后端、工具系统、上下文和会话设计可能完全不同，所以不一定适合直接照搬。
>
> 这一页只简单说明：为什么我们最后可以把第三方 API Gateway 放到 Claude Code 底下，而不再单独维护一套 API runtime。

## 一张图

目前正式 Chat 大致是这样：

~~~text
                         ┌→ Claude 订阅 OAuth
前端 → 后端 → Claude Code runtime
                         └→ Anthropic-compatible API Gateway
                │
                ├→ tools
                ├→ session / resume
                ├→ ContextPlan
                ├→ Continuity
                └→ memory / state
~~~

对我们来说，`provider` 主要决定：

> Claude Code 这一轮从哪里访问模型。

工具、会话、上下文和长期数据继续走原来的系统。

---

## 工具

工具实现主要放在后端，只保留一份。

Claude Code 可以通过：

- 自带只读工具；
- MCP；
- capability proxy；
- 外部 MCP；

访问这些能力。

我们会先决定“系统拥有什么能力”，再决定这一轮实际暴露给 Claude Code 哪些工具。

所以大致可以理解成：

~~~text
业务能力
   ↓
工具绑定 / MCP
   ↓
本轮 allowlist
   ↓
Claude Code
~~~

换 provider 时，不需要跟着重写工具实现。

---

## Session / Resident

正式聊天会保留一个长期运行的 Claude Code resident。

冷启动时会准备比较完整的上下文；后面的 hot turn 主要补：

- 新用户消息；
- 新召回的记忆；
- 发生变化的状态；
- 这一轮新增的信息。

如果 provider、凭证或模型入口改变，就退休旧 resident，下一轮重新冷启动。

不会给已经运行中的进程硬换环境变量。

---

## ContextPlan

“这一轮模型应该看到哪些历史”由我们自己的上下文系统决定。

大致是：

~~~text
数据库历史
   ↓
ContextPlan
   ↓
Claude Code
   ↓
模型
~~~

所以 OAuth 和 API Gateway 不需要各自维护一套历史选择逻辑。

---

## Continuity / 换窗

上下文快满时，我们不会把长期连续性完全交给 Claude Code 自己处理。

系统会自己管理：

- 当前窗口；
- Capacity Swap；
- Continuity Chunk；
- 后续新窗口如何继续前面的语义。

这些内容仍然属于我们自己的长期状态，provider 只负责生成。

---

## Memory

Memory 和原始聊天历史分开。

当前相关的记忆会在需要时召回，再作为这一轮上下文的一部分送进 Claude Code。

它不会因为底层从 OAuth 切到 API Gateway 就换一套实现。

---

## Cache

我们主要关心两类缓存。

第一类是 provider 的 prompt cache，例如：

~~~text
cache_creation_input_tokens
cache_read_input_tokens
~~~

用来观察稳定前缀有没有被复用，以及实际成本。

第二类是 resident 自己带来的上下文复用：

~~~text
cold turn：完整启动
hot turn：只补新增内容
~~~

这两种 cache 解决的问题不同，但都会影响长期运行的成本和延迟。

---

## 后台任务

除了正式 Chat，还有一些后台生成，例如：

- Continuity；
- 压缩；
- 其他一次性生成任务。

如果任务适合 Claude Code runtime，也可以继续走：

~~~text
background job
      ↓
claude -p
      ↓
当前 provider
~~~

这样正式 Chat 和后台生成不用各养一套完全不同的模型入口。

---

## 数据谁说了算

Claude Code session 和 resident 都可以退休、重建。

真正长期保存的东西仍然在自己的系统里，例如：

- 聊天消息；
- 上下文映射；
- Continuity；
- Memory；
- 配置和 provider authority。

所以我们的思路一直是：

> **进程可以重建，长期状态不要只押在进程里。**

---

## 为什么这个仓库对我们适用

我们原本已经有：

- 后端原生工具；
- Claude Code session / resident；
- ContextPlan；
- Continuity；
- Memory；
- 后台生成。

API 再单独维护一套 agent loop 后，很多能力开始出现双份入口。

确认第三方 Gateway 可以完整跑 Claude Code 的 `-p` 和真实工具回合以后，我们就把 API 收到底层 provider，只保留一套 Claude Code runtime。

如果你的项目本来主要围绕 Messages API 构建，或者 Claude Code 只占很小一部分，这个取舍未必适合你。

后面的教程请把它当成一种参考实现，而不是必须采用的架构。
