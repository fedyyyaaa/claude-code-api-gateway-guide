# 4. 接进自己的项目：只换底下的水管

这一篇开始讲架构，但尽量只讲真正需要改的地方。

先记住一句：

> **如果你的工具本来就在后端实现，就让它继续待在那里。**

这次要统一的是 agent runtime，不是重写工具。

---

## 4.1 原来常见的结构

很多自建聊天项目会自然长成：

```text
API
 ↓
后端自己的 tool loop
 ↓
共享后端工具


Claude Code
 ↓
Claude Code agent loop
 ↓
共享后端工具
```

工具已经只有一套。

重复的是上面的 tool loop、session、历史投影和后台生成路径。

---

## 4.2 接进 Claude Code 后

如果 Gateway 已经通过前两篇测试，可以收敛成：

```text
第三方 API Gateway ─┐
                    ├─ Claude Code runtime
Claude 订阅 OAuth ──┘
                           ↓
                     共享后端工具
```

自己的：

- 数据库；
- 工具执行器；
- MCP；
- 权限；
- 记忆系统；
- Context Planner；

都不用因为 API Gateway 重写。

---

## 4.3 provider 只在启动边界选一次

推荐把 provider 选择放在**启动 Claude Code 子进程**的地方。

### 订阅模式

给进程：

```text
CLAUDE_CODE_OAUTH_TOKEN
```

同时清掉：

```text
ANTHROPIC_BASE_URL
ANTHROPIC_AUTH_TOKEN
ANTHROPIC_API_KEY
```

### API Gateway 模式

给进程：

```text
ANTHROPIC_BASE_URL
ANTHROPIC_AUTH_TOKEN
ANTHROPIC_MODEL
```

同时清掉：

```text
CLAUDE_CODE_OAUTH_TOKEN
```

**在这个边界清一次就够。**

内部不需要每一层都重新判断“现在到底是哪家 provider”。

---

## 4.4 Key 从哪里来

正式系统里，Key 应该继续来自你的服务端：

```text
数据库 / secret store / 环境变量
            ↓
     provider selection
            ↓
   Claude Code 子进程环境
```

不要把第三方 API Key 发到浏览器，再让前端传回来。

也不要为了这个教程另造一个新的 credential manager；你原来有安全的密钥来源，就复用它。

---

## 4.5 模型名不要偷偷猜

Gateway 的模型身份最好来自你当前选中的 provider 配置。

例如：

```text
claude-opus-4-6
```

如果模型名拿不到，宁可报一个明确错误，也别悄悄退到某个默认模型。

否则你会很难判断：

> “这次请求到底是谁跑的？”

---

## 4.6 上下文系统不用跟着 provider 重写

如果你的项目已经有：

```text
Memory
Context Plan
Summary
Chunk
Window
Checkpoint
```

推荐继续保持：

```text
数据库
  ↓
自己的上下文系统
  ↓
Claude Code
  ↓
OAuth / API Gateway
```

provider 只决定模型请求往哪里发。

“这一轮应该看到哪些历史”继续由原来的系统决定。
