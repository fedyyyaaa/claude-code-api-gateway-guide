# 5. Provider 切换与长期运行

最小测试很简单，真正上线以后最容易出问题的是：

> 一个 Claude Code 进程已经活着了，这时候用户把 provider 换了怎么办？

答案很朴素：**关掉旧的，下轮重新起。**

---

## 5.1 不给活进程热换环境变量

假设你有一个 resident：

```text
Claude Code process
      ↑
连续很多轮
```

它启动时已经拿到了：

```text
OAuth
```

或者：

```text
ANTHROPIC_BASE_URL + AUTH_TOKEN
```

外面的配置后来改了，**已经启动的进程不会自动得到新的环境变量。**

所以 provider 改变时：

```text
provider changed
      ↓
retire old resident
      ↓
next turn cold start
      ↓
new provider env
```

就够了。

---

## 5.2 不需要双 resident

一般没必要同时养：

```text
一个 OAuth resident
一个 API resident
```

如果你的产品只允许当前对话选择一个 provider，就保留一个当前 resident。

切换时退休，下一句冷启动。

简单很多。

---

## 5.3 session / resume 继续走 Claude Code

Single Runtime 的好处就在这里。

无论底下是：

```text
subscription OAuth
```

还是：

```text
API Gateway
```

上面仍然是 Claude Code。

因此你可以继续复用原本的：

```text
session
resume
agent loop
tools
```

不需要因为 API 另外维护一套会话 runtime。

---

## 5.4 后台任务也可以继续用 `-p`

如果项目有：

- 摘要；
- continuity chunk；
- handoff；
- memory extraction；
- 标题生成；

以前可能分成：

```text
订阅 → claude -p
API  → 自己 requests.post(...)
```

Gateway 能跑 Claude Code 后，可以统一成：

```text
background job
      ↓
claude -p
      ↓
当前 provider
```

这样正式 Chat 和后台任务走同一套 runtime。

---

## 5.5 不要自动偷偷切到付费 API

有一个产品层面的坑很值得单独说：

如果订阅失效、额度用完或 Gateway 挂了，**不要自动换到另一个会产生费用的 provider**。

更安全的行为是：

```text
报错
↓
告诉用户当前 provider 不可用
↓
让用户自己选是否切换
```

因为“自动恢复”很可能等于“自动花钱”。

---

## 5.6 冷启动会比较重

Claude Code 自己会带 system、运行环境信息和工具定义。

所以用户只输入几个 token，并不代表整个请求只有几个 token。

真实测试里，一个非常短的 `-p` 也可能创建几万 token 的 prompt cache。

这不一定代表实际账单就等于 Claude Code 显示的官方列表价，但你应该：

- 看 Gateway 自己的真实扣费；
- 看 cache creation / cache read；
- 再决定是否长期这样跑。
