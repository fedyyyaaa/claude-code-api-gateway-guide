# 5. Provider 切换与长期运行

最小测试很简单，真正上线以后容易混在一起的是：

- resident；
- Claude session；
- `--resume`；
- provider 切换；
- 后台 `-p`。

先给结论：

> **正常聊天一直用同一个 resident；切 provider 时退休旧 resident，并在下一轮新开 Claude session。跨 provider 不复用旧 session。**

---

## 5.1 正常连续聊天：不需要每轮 `--resume`

正式 Chat 用的是一个常驻 Claude Code 子进程：

```text
第一次
启动 claude -p --input-format stream-json
      ↓
得到 session A
      ↓
用户第 1 轮 → stdin
用户第 2 轮 → stdin
用户第 3 轮 → stdin
```

只要 resident 还活着、身份也没变：

**后续回合直接继续喂同一个进程。**

所以正常热聊天：

```text
不会每轮新开进程
也不会每轮 --resume
```

---

## 5.2 切 provider：关旧 resident，新开 session

假设当前是：

```text
OAuth
 ↓
resident A
session A
```

用户切成 API Gateway 后：

```text
provider identity changed
        ↓
retire resident A
        ↓
下一轮 cold start
        ↓
API Gateway 环境变量
        ↓
resident B
session B
```

这里**不会拿 session A 做跨 provider `--resume`**。

连续性由后端负责：

```text
数据库历史
+ ContextPlan
+ Continuity Chunk
      ↓
新的 Claude session
```

所以换 provider 以后，Claude Code 的 session id 可以换，用户看到的对话仍然连续。

### 为什么这样做

旧 session 已经和旧 provider、旧模型、旧运行时状态绑在一起。

如果把它直接 `--resume` 到另一根 Gateway 上，边界会更难证明干净。

我们当前选择很简单：

> **换 provider = 换 Claude session；保留的是后端对话连续性。**

### 跨 provider `--resume` 实验

目前**没有做过“拿 OAuth session 原地 `--resume` 到 Gateway”这种真实实验**。

所以本文不会声称它一定失败，也不会把它写成推荐路线。

当前生产设计主动避开了这个问题。

---

## 5.3 那 `--resume` 什么时候用

我们保留 `--resume <session_id>`，但它属于**明确恢复旧 Claude session**的工具。

例如：

- 进程已经退出；
- 我们有确切的旧 session id；
- 当前恢复路径明确要求继续那份 transcript；
- 特殊 staged restore / deferred tool 恢复。

概念上：

```text
普通 fresh spawn
→ 不带 --resume
→ 新 session

明确恢复旧 session
→ --resume OLD_SESSION_ID

明确创建一个新的命名 session
→ --session-id NEW_SESSION_ID
```

所以 `--resume` 是恢复手段，不是每轮聊天的默认机制。

---

## 5.4 后台 `-p`：每个任务独立

摘要、Chunk、handoff 这类后台任务不要塞进正式 resident。

我们当前做法是 one-shot：

```text
任务 1 → claude -p → 完成 → 退出
任务 2 → claude -p → 完成 → 退出
```

并使用：

```text
--no-session-persistence
```

它们不需要 `--resume`。

这样后台任务不会把“写摘要”“做压缩”之类的指令污染正式聊天 session。

---

## 5.5 resident 不能并发写

一个 Claude Code resident 不能安全地同时处理两轮 stdin。

所以后端必须先做串行化：

```text
turn A 正在跑
      ↓
turn B 到达
      ↓
等待 / 排队 / 明确让路
```

不要出现：

```text
两个请求
同时往同一个 Claude stdin 写
```

我们的当前实现会用生成锁把同一 resident 的 turn 串起来；主动消息和用户消息撞在一起时，也不能交错写同一个 resident。

多用户场景会复杂很多，这也是 README 把完整教程限定在单用户自用环境的原因之一。

---

## 5.6 崩溃、空闲和超时怎么处理

### 进程崩了

如果 resident 已经死亡：

```text
下一轮发现 process dead
      ↓
cold start / 恢复路径
```

不要假装旧进程还可复用。

### 空闲回收

长期在线的 resident 不必永远挂着。

我们当前实现里，成功使用后空闲超过约 **3 小时** 会进入 idle respawn 路径。

这个数字只是当前项目的选择，不是 Claude Code 的要求。

### 一轮卡死

无人值守环境要同时有：

- inactivity / stall timeout；
- absolute hard timeout。

当前项目会区分“长时间没有 provider 活动”和“一整轮已经跑得太久”，超时后终止不确定的 resident，再让后续回合走恢复 / cold start。

具体秒数按自己的任务长度调，不建议照抄我们的值。

---

## 5.7 用户打断时，先看请求有没有真正发出去

打断不能一律当成同一种情况。

### provider 还没看到这一轮

如果 stdin 还没有真正 flush：

```text
取消
↓
释放本轮 lease
↓
resident 可以继续保留
```

因为上游根本没见过这条消息。

### provider 已经开始处理

如果 stdin 已经发出去，或者已经出现 provider event：

```text
取消 / 断流
↓
这一轮状态可能不完整
↓
别把 resident 当成确定干净
↓
按失败恢复规则处理
```

宁可下一轮重新冷启动，也不要在不知道 Claude session 已经写进去多少内容时继续热复用。

---

## 5.8 冷启动和切 provider 的代价

换 provider 后第一次请求通常会更慢、更贵一点：

- 新 Claude Code 进程要启动；
- 新 session 要建立；
- 旧 provider 的 prompt cache 不能直接当成新 provider 的 cache；
- 大段固定 system / tools 可能重新写缓存。

所以：

> **切换能力解决的是可用性和架构统一，不代表切换本身零成本。**

频繁左右横跳 provider，会损失缓存收益。

---

## 5.9 日志要记什么

长期运维时，建议至少能看到：

- resident 是否存活；
- spawn / respawn 原因；
- 当前 provider 类型；
- 模型 identity；
- session id（最好只记 hash / 截断值）；
- 每轮输入、输出、cache read / creation；
- stall / hard timeout；
- 进程资源占用。

不要记录：

- 完整 OAuth token；
- Gateway Key；
- 带密钥的环境变量；
- 不必要的完整 provider stderr。

---

## 5.10 不要自动偷偷切到付费 API

如果订阅失效、额度用完或 Gateway 挂了：

```text
报错
↓
告诉用户当前 provider 不可用
↓
让用户自己选择是否切换
```

“自动恢复”很可能等于“自动花钱”。
