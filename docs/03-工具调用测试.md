# 3. 第二关：让 Claude Code 真正调一次工具

普通 `-p` 能回字，只能证明文本请求能走通。

如果你准备把这个 Gateway 放进 Claude Code runtime，**工具回合一定要测。**

---

## 3.1 用 Bash 做一个最小探针

运行：

```bash
claude   --no-session-persistence   --allowedTools Bash   -p '必须调用 Bash 执行：
printf TOOL_OK > ./tool_probe.txt && cat ./tool_probe.txt
确认工具结果后，最终只回复 TOOL_OK。'   --output-format json
```

然后检查文件：

```bash
cat ./tool_probe.txt
```

正常应该看到：

```text
TOOL_OK
```

最终模型回复也应该是：

```text
TOOL_OK
```

测试结束后可以删掉：

```bash
rm -f ./tool_probe.txt
```

---

## 3.2 这一步到底验证了什么

这一个小测试同时走过了：

```text
Claude Code
  ↓
Gateway
  ↓
模型返回 tool_use
  ↓
Claude Code 执行 Bash
  ↓
tool_result
  ↓
再次经过 Gateway
  ↓
模型给出最终回复
```

所以它比“能聊天”重要得多。

成功后，至少可以确认：

- **Gateway 没弄坏 tool use 结构**
- **Claude Code 能识别工具调用**
- **工具结果可以继续喂回模型**
- **一个完整 agent loop 能结束**

---

## 3.3 如果你没有 Bash

换成你本机允许的一个**无副作用工具**也可以。

原则只有一个：

> 不要只让模型“说它会调工具”，要确认工具真的执行过。

如果你自己的系统已经把后端工具通过 MCP 暴露给 Claude Code，也可以直接挑一个只读工具做测试，例如：

```text
get_status
list_files
search_memory
```

第一次别拿“发邮件、删文件、付款”这种有副作用的工具测。

---

## 3.4 通过以后再做什么

到这里，你已经有了最重要的两个证据：

```text
-p 文本请求 ✅
真实工具回合 ✅
```

如果你只想在本机用第三方 API 跑 Claude Code，到这里其实已经够用了。
