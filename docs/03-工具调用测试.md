# 3. 第二关：让 Claude Code 真正调一次工具

普通 `-p` 能回字，只能证明文本请求能走通。

如果你准备把这个 Gateway 放进 Claude Code runtime，**工具回合一定要测。**

---

## 3.1 用 Bash 做一个最小探针

运行：

```bash
claude \
  --no-session-persistence \
  --allowedTools Bash \
  -p '必须调用 Bash 执行：
printf TOOL_OK > ./tool_probe.txt && cat ./tool_probe.txt
确认工具结果后，最终只回复 TOOL_OK。' \
  --output-format json
```

然后检查文件：

```bash
cat ./tool_probe.txt
```

正常应该看到：

```text
TOOL_OK
```

最终模型回复也应该是：

```text
TOOL_OK
```

测试结束后可以删掉：

```bash
rm -f ./tool_probe.txt
```

---

## 3.2 这一步到底验证了什么

这一个小测试同时走过了：

```text
Claude Code
  ↓
Gateway
  ↓
模型返回 tool_use
  ↓
Claude Code 执行 Bash
  ↓
tool_result
  ↓
再次经过 Gateway
  ↓
模型给出最终回复
```

所以它比“能聊天”重要得多。

成功后，至少可以确认：

- **Gateway 没弄坏 tool use 结构**
- **Claude Code 能识别工具调用**
- **工具结果可以继续喂回模型**
- **一个完整 agent loop 能结束**

---

## 3.3 三种常见失败，怎么看

### 最终没有 `tool_probe.txt`

说明工具没有真正执行成功。

先看终端里的错误状态和退出码，别因为模型最后说了“完成”就算通过。

### 出现 permission denied，或者一直等确认

说明 headless 权限没有放行这次工具调用。

Claude Code 当前官方故障排查也提醒：版本升级后，非交互 `claude -p` 如果没有明确 permission mode，工具调用可能出现 permission denial。

先确认当前版本的权限设置，再重跑探针。

官方参考（核对日期：**2026-11-13**）：

https://code.claude.com/docs/en/troubleshooting

### 模型回复了 `TOOL_OK`，文件却不存在

**探针失败。**

模型只是口头声称执行过工具，并不能证明 tool loop 真走完。

这里最可靠的证据就是：

```text
文件真的存在
+
内容真的是 TOOL_OK
```

不需要为了证明这一点贴整份 JSON 日志。

## 3.4 如果你没有 Bash

换成你本机允许的一个**无副作用工具**也可以。

原则只有一个：

> 不要只让模型“说它会调工具”，要确认工具真的执行过。

如果你自己的系统已经把后端工具通过 MCP 暴露给 Claude Code，也可以直接挑一个只读工具做测试，例如：

```text
get_status
list_files
search_memory
```

第一次别拿“发邮件、删文件、付款”这种有副作用的工具测。

```text
-p 文本请求 ✅
```
